## 2. Реконструкция тезисов статьи

Статья — ответ на популярный нарратив «IDE больше не нужна, все живут в терминале с Claude Code /
Codex / OpenCode».

**Т1. У тезиса «IDE не нужна» слабое место: он смотрит на IDE глазами человека.** 🟡
Следующий пользователь IDE — не человек, а агент. Вопрос не «нужен ли редактор», а
«кто отдаёт агенту семантику проекта».

**Т2. `grep`/`find` слепы к структуре проекта, границам символов и семантике языка.** 🟡
Агент жжёт токены, просеивая шумный вывод, и делает лишние вызовы, чтобы сузить поиск.

**Т3. Решение — отдать агенту индексный поиск IDE.** 🟡
JetBrains делает skill, который связывает поисковый промпт с **единым** MCP-инструментом,
покрывающим поиск по файлам, по тексту, по regex и по символам. Ключевое слово — «единым»:
не 4 инструмента, а один с режимами.

**Т4. IDE как база знаний о проекте — пример `finding-tests`.** 🟡
Когда агент пишет новый код или меняет поведение, активируется skill поиска тестов.
В Rider он берёт данные покрытия из **dotCover**, чтобы вернуть пути к тестам, связанным
с изменённым кодом, без ручного поиска по проекту.

**Т5. Двойная поставка.** 🟡
Одна и та же возможность отдаётся двумя способами: как **bundled skill** для встроенного
AI Assistant и как **отдельный MCP-инструмент `findTests`** для внешних агентов —
Claude Code, Codex. Это и есть архитектурный вывод статьи.

**Т6. Junie для Rider вышел отдельным плагином.** 🟡

**Т7. Общий вывод.** 🔴 (моя формулировка)
IDE перестаёт быть «редактором с автодополнением» и становится **сервисом двух вещей для агента**:
инструментов (индекс, рефакторинги, run-конфигурации, отладчик, покрытие) и знаний о проекте
(модель домена, эндпоинты, бины, тесты). Транспорт — MCP; интерактивный режим — ACP.

## 3. Адверсариальный разбор

### 3.1. Что в статье верно

- **Семантика действительно нужна.** Разница между «найди строку `UserService`» и
  «найди объявление символа `UserService` и все его использования» — реальная, и второе
  дешевле по токенам на больших кодовых базах. ✅ (это свойство индекса, а не маркетинг)
- **Разделение «bundled skill / внешний MCP-инструмент» — правильная развилка.** ✅
  Внутренний агент IDE и внешний CLI-агент — разные потребители, и попытка обслужить их
  одним интерфейсом обычно кончается плохо.
- **`.claude/`-слой важнее модели.** Это общее место серии, и оно подтверждается
  документацией Claude Code: skills, hooks, subagents, permissions — всё это первоклассные
  механизмы, а не обвязка. ✅

### 3.2. Чего в статье нет и что это меняет

**A. Нет ни одного измерения.** 🔴
Центральное утверждение — «агент жжёт токены на grep» — не сопровождается ни числом токенов,
ни pass rate, ни временем. Без A/B это гипотеза. Контрпример, который легко воспроизвести:
`ripgrep` по монорепе в 300k строк отдаёт результат за ~0.2 с и укладывается в 200–800 токенов,
если агент сразу указывает `glob` и `-n`. MCP-вызов в IDE — это round-trip через сокет
к JVM-процессу, и он не бесплатный ни по времени, ни по токенам.

**B. Конфликт интересов.** 🟡
Haulmont — вендор Amplicode и OpenIDE. Статья в корпоративном блоге, и рекомендуемая
архитектура ведёт к их коммерческому плагину. Это не делает тезисы ложными, но означает,
что независимой проверки в тексте нет и её надо провести самому.

**C. Сама MCP-интеграция стоит токенов — и статья это не считает.** ✅
Описания MCP-инструментов лежат в контексте постоянно, до первого вызова. Spring MCP от
Amplicode — это минимум 11 инструментов (`get_project_summary`, `list_module_dependencies`,
`get_entity_details`, `get_jdbc_entity_details`, `list_entity_repositories`, `list_entity_services`,
`list_entity_mappers`, `list_entity_dtos`, `list_entity_controllers`, `list_all_domain_entities`,
`list_project_endpoints` — ✅ вычитано из `skills/spring-explore/SKILL.md`), плюс ~20 инструментов
встроенного MCP-сервера IDEA. Claude Code предупреждает, когда вывод MCP-инструмента превышает
10 000 токенов, и по умолчанию режет на 25 000 (`MAX_MCP_OUTPUT_TOKENS`) ✅.
То есть «подключим MCP, чтобы сэкономить токены» — частично самоопровергающийся ход.
**Правильная форма аргумента:** экономит не MCP сам по себе, а *skill, который вызывает MCP
точечно и только когда нужно*. Именно так и устроен `spring-explore` (шаг 1 — явно решить,
какие пути исследования пропустить; шаг 4 — выполнить план вызовов в субагенте, чтобы сырой
вывод не попал в основной контекст) ✅. Это хороший дизайн, но в статье он не назван как
условие экономии.

**D. Два пути к одной цели ломают выбор модели.** 🔴
После подключения IDE MCP у агента появляются `search_in_files_by_text` **и** встроенный `Grep`;
`reformat_file` **и** `./gradlew spotlessApply`; `execute_run_configuration` **и** `Bash`.
Модель будет выбирать непредсказуемо. Без явного правила «кто когда» в `CLAUDE.md` вы
получаете не ускорение, а дисперсию. Это устраняется за 10 строк — см. шаблон
[`templates/CLAUDE.md`](./templates/CLAUDE.md).

**E. IDE — это состояние, а состояние отказывает.** 🟡
IDE должна быть запущена и проиндексирована. Пока идёт индексация после `git pull` или
переключения ветки, IDE в dumb mode, и «умные» запросы либо ждут, либо отдают неполный ответ.
У JetBrains есть публичные баги ровно этого класса (например, `RIDER-128984`: project-related
MCP-инструменты возвращают пустой список) 🟡. Агент, у которого поиск — единственный путь
через IDE, в этот момент не деградирует, а *врёт*: пустой список неотличим от «ничего не найдено».

**F. Headless-режима нет вообще.** ✅
Claude Code на CI, в GitHub Actions, в Claude Code on the web — это среда без запущенной IDE.
Вся архитектура «знания живут в IDE» там не работает. Значит, любой skill, который зависит
от IDE-MCP, обязан иметь фолбэк на инструменты сборки, иначе один и тот же промпт даёт
разный результат локально и в CI. Это ключевое требование, которого в статье нет.

**G. `finding-tests` через coverage имеет системную слепую зону.** 🔴
Покрытие отвечает на вопрос «какие тесты трогали этот код **в прошлом прогоне**». Для нового
кода покрытия нет по определению. Для изменённого поведения покрытие устаревает ровно в момент
изменения. То есть инструмент даёт максимум пользы там, где код и так покрыт, и молчит там,
где риск выше всего. Фолбэк по конвенции имён (`FooService` → `FooServiceTest`) и по структуре
модуля обязателен.

**H. Skills нестабильны в триггеринге — и это признаёт сам источник.** 🟡
Из харнесс-статьи Haulmont: один skill активируется почти всегда, даже когда не нужен; другой
не включается в нужный момент; третий срабатывает «в паре» с соседним, и они мешают друг другу.
**Вывод, который отсюда следует, а в основной статье не сделан:** всё, что должно выполняться
детерминированно (компиляция, формат, ArchUnit, миграции), нельзя вешать на срабатывание skill.
Это уровень **hooks** и **CI**. Skills — для знаний и процедур, hooks — для гарантий.

**I. Vendor lock и воспроизводимость.** 🟡
`findTests` — специфика IDEA/Rider. Amplicode — коммерческий плагин. Skills из
`Amplicode/spring-skills` открыты (Apache-стиль репозиторий), но их шаги 2–4 явно требуют
Spring MCP, то есть плагина ✅ («The skill requires the Amplicode IntelliJ plugin and its MCP
server to function»). Команда без плагина получит skill, который уверенно ссылается на
несуществующие инструменты — худший из возможных отказов.

**J. Поставка через `curl | bash`.** ✅
Официальный установщик — `curl -fsSL .../install.sh | bash`. Скрипт клонирует репозиторий в
`~/.agents/.amplicode/spring-skills/`, раскладывает симлинки в `~/.agents/skills/`,
`~/.kilocode/skills/`, `~/.veai/skills/`, `~/.qwen/skills/`, а для Claude Code — выполняет
`claude plugin marketplace add <repo>` и ставит плагин `spring-tools@spring-tools`.
Это изменение глобальной конфигурации агента из сетевого скрипта. Разбор — в разделе 7.

### 3.3. Итог разбора

Направление статьи верное, реализация «всё через IDE-MCP» — хрупкая. Рабочая архитектура — трёхслойная,
и слои нельзя менять местами:

```
Слой 3  Skills / субагенты      — знания и процедуры. Мягкие, вероятностные.
        (spring-*, свои)          Дают качество. Не дают гарантий.
           ↑ вызывает точечно
Слой 2  IDE MCP + Spring MCP    — семантика и структура. Быстро, но требует
        (index, symbols,          запущенной IDE. Ускоритель, не фундамент.
         entities, endpoints)     ОБЯЗАН иметь фолбэк.
           ↑ опирается на
Слой 1  Gradle/Maven, javac,    — детерминированный фундамент. Работает
        тесты, hooks, CI          локально и в CI одинаково. Даёт гарантии.
```

Если у вас есть время только на один слой — делайте первый. Слой 2 без слоя 1 —
это ускорение движения в неизвестном направлении.

## 4. Что IDE даёт сама по себе

Три независимых механизма, которые часто путают.

### 4.1. Плагин Claude Code для JetBrains ✅

Ставится с JetBrains Marketplace («Claude Code [Beta]», plugin id 27310), **не** тащит с собой CLI —
нужен отдельно установленный `claude` в PATH.

Что даёт:

- `Cmd+Esc` / `Ctrl+Esc` — запуск из редактора;
- **диффы в нативном вьювере IDE** вместо терминала (`/config` → Diff tool → `auto`);
- **контекст выделения**: текущее выделение и путь активного файла уезжают в промпт автоматически
  (в транскрипте видно `⧉ Selected N lines from <file>`);
- `Cmd+Option+K` / `Alt+Ctrl+K` — вставка ссылки вида `@src/auth.ts#L1-99`;
- **диагностика IDE** (инспекции, ошибки компиляции, линт) уезжает Клоду автоматически;
- из внешнего терминала — команда `/ide` для подключения.

Под капотом плагин поднимает локальный MCP-сервер с именем `ide`, скрытый из `/mcp`.
Модели из него видна **ровно одна** функция:

| Инструмент | Что делает | Read-only |
|---|---|---|
| `mcp__ide__getDiagnostics` | Инспекции IDE — ошибки и предупреждения редактора, опционально по одному файлу | да |

В JetBrains-версии плагина **нет** инструмента исполнения кода (в отличие от VS Code, где есть
`mcp__ide__executeCode` для Jupyter). Транспорт — незашифрованный `ws://` на loopback,
токен в `~/.claude/ide/<port>.lock`.

> Практический вывод: `mcp__ide__getDiagnostics` — самый недооценённый инструмент во всей связке.
> Он бесплатно отдаёт результат работы полноценного Java-анализатора IDEA, включая то,
> что `javac` не показывает: nullability, unused, неверные Spring-аннотации, битые `@Value`-плейсхолдеры,
> ошибки в JPQL внутри `@Query`. Это дешевле, чем гонять сборку.

**Риск, задокументированный Anthropic:** в режиме `acceptEdits` внутри JetBrains Клод может
править конфигурационные файлы IDE, которые IDE исполняет автоматически — это обход
permission-промптов на bash. Рекомендация из доков: не использовать `acceptEdits` в IDE
на недоверенных промптах. ✅

### 4.2. Встроенный MCP-сервер IntelliJ IDEA 🟡

Отдельная вещь, не связанная с плагином Claude Code. Идёт в комплекте с IDE начиная с **2025.2**,
плагин «MCP Server» включён по умолчанию.

Включение: **Settings → Tools → MCP Server → Enable MCP Server**. Для распознанных клиентов
(Junie, Claude Code, Codex, VS Code, Copilot CLI) конфигурация проставляется автоматически;
вручную — кнопка **Copy Stdio Config**, вставить в конфиг Claude Code.
Порядок предпочтения транспорта для Claude Code: **stdio → HTTP stream → SSE**.

Что отдаёт (имена подтверждены поиском, но не вычитаны из официальной страницы — проверьте
через `/mcp` после подключения):

| Группа | Инструменты |
|---|---|
| Поиск и навигация | поиск символов, инфо о символе, символы файла, иерархия типов, `search_in_files_by_text` |
| Анализ | `get_file_problems` (инспекции) |
| Рефакторинг | `rename_refactoring` (переименование с обновлением всех ссылок) |
| Формат | `reformat_file` |
| Запуск | `execute_run_configuration`, терминал |
| Отладка | контекст отладчика |
| БД | опциональные database-инструменты |

Это тот самый «единый MCP-инструмент поиска», о котором пишет статья — только на практике
он всё же разбит на несколько.

### 4.3. ACP — Agent Client Protocol 🟡

Открытый стандарт (Zed + JetBrains + Anthropic): агент живёт отдельным процессом и общается с
редактором по JSON-RPC 2.0 через stdin/stdout — то же, чем LSP является для языковых серверов.
Практический смысл: агент рисуется в IDE как первоклассный UI (диффы, планы, аппрувы), а не как
текст в терминале. Для Claude Code сегодня штатный путь — плагин из 4.1; ACP актуален,
если вы смотрите в сторону OpenIDE/Zed или пишете свой агент.

| `java-debug` | in progress | Отладка через IntelliJ MCP |

Обратите внимание: половина того, что продаётся как готовый тулкит, помечена **in progress**
самим вендором. Это не упрёк — это причина не строить на них процесс.

**Устройство `spring-explore`** (стоит изучить как образец, даже если сам тулкит не ставите):
шаг 0 — предсказать, что в проекте есть, **не вызывая инструментов**; шаг 1 — по каждому пути
исследования явно решить include/skip с обоснованием; шаг 2 — подгрузить только нужные референсы;
шаг 3 — собрать единый нумерованный план вызовов MCP; шаг 4 — **выполнить его в субагенте**
и вернуть полный результат с редактированием секретов; шаг 5 — синтез отчёта; шаг 5.5 —
явно назвать неозвученные ожидания пользователя (валидация, коды ошибок, формат ответа, авторизация);
шаг 6 — решить, нужен ли ещё цикл.

Шаги 0, 1 и 4 — это ровно те приёмы, которые экономят контекст. Их стоит скопировать
в свои скиллы независимо от Spring.

## 5. Инструкция: настройка Claude Code уровнями 0→4

Уровни независимы и проверяемы. Не переходите к следующему, пока текущий не даёт эффекта —
иначе вы не поймёте, что именно помогло.

### Уровень 0. Детерминированный фундамент (обязательно)

Без него всё остальное — украшение.

1. **`CLAUDE.md` в корне проекта.** Не «описание проекта», а свод правил, которые Клод нарушает
   чаще всего. Шаблон: [`templates/CLAUDE.md`](./templates/CLAUDE.md).
2. **Быстрая команда проверки.** Одна команда, которая за <30 с говорит «сломано / не сломано»:
   ```bash
   ./gradlew --offline compileJava compileTestJava spotlessCheck -q
   ```
3. **Hook на изменение Java-файла.** Компиляция + формат сразу после `Edit`/`Write`, результат
   возвращается Клоду. Файлы:
   [`templates/settings.json`](./templates/settings.json),
   [`templates/hooks/java-change-gate.sh`](./templates/hooks/java-change-gate.sh).
4. **Permissions.** Разрешить `./gradlew`, `git status/diff/log`; спрашивать на `git push`,
   `./gradlew bootRun`; запретить чтение `.env`, `**/application-prod*.yml`.

Проверка уровня: попросите Клода внести заведомо не компилирующееся изменение. Он должен
узнать об этом сам, без вашего сообщения.

### Уровень 1. Подключить IDE как источник диагностики

1. Установить плагин **Claude Code [Beta]** из JetBrains Marketplace, перезапустить IDE.
2. Убедиться, что `claude` в PATH (`claude --version`). Если нет — прописать полный путь в
   **Settings → Tools → Claude Code [Beta] → Claude command**.
3. Запускать `claude` из встроенного терминала IDE (тогда всё активно сразу) либо
   `/ide` из внешнего терминала — ждём `Connected to IntelliJ IDEA.`
4. `/config` → **Diff tool** → `auto`.
5. Добавить в `CLAUDE.md` правило:
   > После правки Java-кода вызови `mcp__ide__getDiagnostics` по изменённым файлам,
   > прежде чем запускать сборку. Инспекции IDEA ловят то, чего не видит `javac`.
6. ESC не прерывает Клода в терминале IDEA? **Settings → Tools → Terminal** → снять
   «Move focus to the editor with Escape».

Проверка уровня: выделите метод в редакторе и спросите «что здесь не так» — Клод должен
увидеть выделение без явного указания файла.

### Уровень 2. Встроенный MCP-сервер IDEA

1. **Settings → Tools → MCP Server → Enable MCP Server**.
2. Если Claude Code не подхватился автоматически — **Copy Stdio Config**, вставить в
   `~/.claude.json` (scope `local`) или `.mcp.json` проекта. Форма — см.
   [`templates/.mcp.json`](./templates/.mcp.json).
3. В Claude Code: `/mcp` → сервер должен быть `connected`. **Выпишите реальные имена
   инструментов** — от них зависят permission-правила.
4. **Сузьте surface.** Инструменты записи и исполнения не должны идти без спроса:

   ```jsonc
   "permissions": {
     "allow": [
       "mcp__jetbrains__get_file_problems",
       "mcp__jetbrains__search_in_files_by_text",
       "mcp__jetbrains__get_symbol_info"
     ],
     "ask": [
       "mcp__jetbrains__rename_refactoring",
       "mcp__jetbrains__execute_run_configuration",
       "mcp__jetbrains__reformat_file"
     ]
   }
   ```
5. **Снимите конфликт «два пути к одной цели»** — правило в `CLAUDE.md`
   (см. секцию «Разделение инструментов» в шаблоне).

Проверка уровня: попросите «переименуй `UserService.findAll` в `listAll` во всём проекте».
Правильное поведение — `rename_refactoring` с запросом подтверждения, а не 15 вызовов `Edit`.

> **Не пропускайте:** если IDE не запущена или индексируется, эти инструменты молчат или врут
> пустым ответом. Фолбэк на `Grep`/`Glob` должен быть прописан явно, иначе Клод примет
> пустой список за отсутствие кода.

### Уровень 3. Spring Agent Toolkit — по желанию и с оговорками

Ставьте, **только** если: (а) вы работаете в IDEA/OpenIDE, (б) готовы к коммерческому
плагину Amplicode, (в) уровни 0–2 уже дают эффект.

Безопасная установка вместо `curl | bash`:

```bash
git clone https://github.com/Amplicode/spring-skills ~/.agents/.amplicode/spring-skills
less ~/.agents/.amplicode/spring-skills/install.sh     # прочитать
claude plugin marketplace add ~/.agents/.amplicode/spring-skills
claude plugin install spring-tools@spring-tools
```

Затем включить Spring MCP: **Settings → Tools → Amplicode → MCP Server → Enable**
(`http://127.0.0.1:64442/sse`).

**Обязательное дополнение**, которого нет в поставке: правило деградации. Добавьте в `CLAUDE.md`:

> Скиллы `spring-*` требуют Spring MCP. Перед их использованием проверь, что инструмент
> `get_project_summary` доступен. Если нет — не имитируй его вывод: скажи об этом и работай
> через `Grep`/`Glob` и `./gradlew`.

Проверка уровня: выключите Spring MCP и повторите тот же промпт. Если Клод продолжает
уверенно «знать» структуру проекта — он галлюцинирует, правило не сработало.

### Уровень 4. Свои скиллы, субагенты и ворота

Это то, что даёт наибольший прирост на длинной дистанции, потому что кодирует ваш проект,
а не абстрактный Spring.

- **Skill-ворота на изменение:** [`templates/skills/spring-change-gate/SKILL.md`](./templates/skills/spring-change-gate/SKILL.md)
- **Skill выбора источника контекста (IDE или фолбэк):** [`templates/skills/ide-context/SKILL.md`](./templates/skills/ide-context/SKILL.md)
- **Субагент-исследователь (read-only, отдельный контекст):** [`templates/agents/spring-explorer.md`](./templates/agents/spring-explorer.md)

Три приёма из `spring-explore`, которые стоит применять в любом своём скилле:

1. **Предсказать до вызова.** Заставьте модель сначала выписать гипотезу о структуре,
   потом проверять её вызовами. Это режет количество вызовов вдвое.
2. **Явный include/skip.** Не «исследуй проект», а «по каждому из путей скажи, берём или нет,
   и почему». Пропуск с обоснованием дешевле, чем неявный пропуск.
3. **Сырой вывод — в субагента.** Тонны JSON от MCP не должны попадать в основной контекст.
   Пусть субагент вернёт синтез.

## 6. Улучшение harness под Spring

Здесь — то, чего в статье нет вообще, а на практике это даёт больше, чем IDE-MCP.

### 6.1. Сделайте цикл обратной связи быстрым

Агент хорош ровно настолько, насколько быстро узнаёт, что ошибся. Полный
`./gradlew build` в Spring-проекте — это 3–10 минут, и это провал: агент либо ждёт,
либо не проверяет.

| Приём | Эффект |
|---|---|
| `./gradlew compileJava compileTestJava` вместо `build` в hook'е | секунды вместо минут |
| `--offline` в проверочных командах | убирает сетевые таймауты |
| Gradle daemon + configuration cache (`org.gradle.configuration-cache=true`) | -30–60% на повторных запусках |
| Testcontainers reuse (`testcontainers.reuse.enable=true` в `~/.testcontainers.properties`) | контейнер не пересоздаётся между прогонами |
| `spring.docker.compose.skip.in-tests=true` | не поднимать compose на юнит-тестах |
| Срезы (`@DataJpaTest`, `@WebMvcTest`, `@JsonTest`) вместо `@SpringBootTest` | один контекст вместо N |
| `@DirtiesContext` — запретить в `CLAUDE.md` без обоснования | главный убийца кэша контекстов |

Правило для `CLAUDE.md`: **запускать только затронутые тесты**, полный прогон — на `Stop`-hook
или в CI.

### 6.2. Детерминированные ворота вместо надежды на skill

Помните признание из харнесс-статьи: скиллы срабатывают непредсказуемо. Поэтому всё,
что должно выполняться **всегда**, вешайте на hooks:

| Событие | Что проверять |
|---|---|
| `PostToolUse` / `Edit\|Write` по `*.java` | компиляция затронутого модуля + `spotlessApply` + `mcp__ide__getDiagnostics` |
| `PostToolUse` по `src/main/resources/db/**` | валидность миграции (`./gradlew flywayValidate` / `liquibase validate`) |
| `PostToolUse` по `*Entity.java` | **есть ли миграция в этом же изменении** — самая частая ошибка агента |
| `Stop` | затронутые тесты + ArchUnit |
| `UserPromptSubmit` | подмешать ветку, JDK, активный профиль, версию Spring Boot |
| `SessionStart` | предупредить, если IDE не подключена и IDE-MCP недоступен |

Готовый скрипт: [`templates/hooks/java-change-gate.sh`](./templates/hooks/java-change-gate.sh).

### 6.3. ArchUnit как исполняемый `CLAUDE.md`

Самый недооценённый инструмент для агентной разработки на Spring. Правила в прозе Клод
нарушает; правила как падающий тест — нет.

```java
@AnalyzeClasses(packages = "com.acme.app", importOptions = DoNotIncludeTests.class)
class ArchitectureTest {

    @ArchTest
    static final ArchRule noFieldInjection = noFields()
        .should().beAnnotatedWith(Autowired.class)
        .because("используем constructor injection");

    @ArchTest
    static final ArchRule controllersDoNotTouchRepositories = noClasses()
        .that().areAnnotatedWith(RestController.class)
        .should().dependOnClassesThat().areAnnotatedWith(Repository.class);

    @ArchTest
    static final ArchRule entitiesDoNotLeakToWeb = noClasses()
        .that().resideInAPackage("..web..")
        .should().dependOnClassesThat().areAnnotatedWith(Entity.class)
        .because("наружу отдаём DTO");

    @ArchTest
    static final ArchRule servicesAreTransactional = classes()
        .that().areAnnotatedWith(Service.class)
        .should().resideInAPackage("..service..");
}
```

Одна фраза в `CLAUDE.md` — «архитектурные правила закодированы в `ArchitectureTest`,
запускай его после структурных изменений» — заменяет полстраницы прозы.

### 6.4. Правила `CLAUDE.md`, которые реально меняют выход на Spring

Отобраны по принципу «Клод ошибается здесь чаще всего»:

- Constructor injection, без `@Autowired` на полях. Зависимости — `private final`.
- `@Transactional` — на сервисном слое, не на контроллере и не на репозитории.
  Читающие методы — `@Transactional(readOnly = true)`.
- **Изменение `@Entity` без миграции — незавершённая работа.** `ddl-auto` — только `validate`.
- Ленивые связи по умолчанию; для списков в ответе — `join fetch` или `@EntityGraph`.
  Проверять N+1 через `hibernate.generate_statistics` в тестовом профиле.
- Наружу — DTO, никогда не сущности. Маппер — по образцу существующих в проекте.
- Конфиги — `@ConfigurationProperties` с валидацией, не россыпь `@Value`.
- Исключения — через `@RestControllerAdvice` + `ProblemDetail` (RFC 7807), не `ResponseEntity` в каждом методе.
- Новый эндпоинт → интеграционный тест среза + запись в OpenAPI.
- Никаких `System.out.println`, только SLF4J; без строковой конкатенации в логах.
- Версии зависимостей — только через Spring Boot BOM, без ручных версий.

### 6.5. Context7 MCP — против устаревших знаний о Spring

Spring Boot 3.x/4.x меняет API быстрее, чем обновляются веса модели. Подключите Context7
и добавьте правило: перед использованием незнакомого API Spring — свериться с документацией
под ту версию, что в `build.gradle`. Это дешевле, чем ловить `NoSuchMethodError` на CI.

### 6.6. Разделение труда между слоями (шпаргалка)

| Задача | Чем делать | Почему не иначе |
|---|---|---|
| Найти строку/паттерн | `Grep` | быстрее MCP, работает в CI |
| Найти объявление символа и usages | IDE MCP | grep даст ложные срабатывания |
| Переименовать символ | IDE MCP `rename_refactoring` | серия `Edit` порвёт ссылки |
| Понять модель домена | Spring MCP / субагент-исследователь | чтение 40 файлов сожжёт контекст |
| Отформатировать | `spotlessApply` в hook | детерминированно, работает в CI |
| Узнать ошибки | `mcp__ide__getDiagnostics` + `compileJava` | два независимых источника |
| Гарантировать инвариант | hook или ArchUnit | skill может не сработать |
| Передать знание о проекте | skill / `CLAUDE.md` | это не инструмент, это контекст |

## 7. Безопасность: чек-лист перед включением

1. **`curl | bash` не запускать вслепую.** Установщик Amplicode модифицирует глобальную
   конфигурацию агента: регистрирует marketplace, ставит плагин, раскладывает симлинки
   в каталоги пяти разных агентов. Клонируйте, читайте, ставьте локально (см. уровень 3).
2. **Project skills умеют выдавать себе права.** Документация Claude Code прямо предупреждает:
   `allowed-tools` в `.claude/skills/` начинает действовать после принятия workspace trust,
   так что skill из чужого репозитория может выдать себе широкий доступ к инструментам.
   Ревьюйте `.claude/` в PR так же, как код.
3. **`acceptEdits` внутри JetBrains — повышенный риск.** Клод может править конфиги IDE,
   которые IDE исполняет сама, обходя permission-промпты на bash. В IDE держите ручное
   подтверждение правок.
4. **Не включайте «Accept connections from all network interfaces»** в настройках плагина
   Claude Code без крайней нужды: транспорт — незашифрованный `ws://`, и токен уходит
   по сети в открытом виде. Для WSL2 предпочтительнее mirrored networking.
5. **Deny-правила на секреты.** `Read` deny на `.env`, `**/application-prod*.yml`,
   `**/*secret*` блокирует не только чтение файла, но и утечку выделения из редактора
   в промпт.
6. **Database-инструменты IDE MCP** — отдельный риск: они дают агенту доступ к настроенным
   в IDE подключениям, включая прод. Отключайте, если не нужны.
7. **`execute_run_configuration`** = произвольное исполнение с профилями и переменными
   окружения из IDE. Только `ask`.

## 8. Как измерить, что стало лучше

Главная претензия к статье — отсутствие измерений. Не повторяйте её.

- **`/usage` в Claude Code** даёт атрибуцию расхода **по скиллам, субагентам, плагинам
  и MCP-серверам** ✅. Это готовый ответ на вопрос «окупается ли этот MCP».
- Возьмите 5–10 типовых задач вашего проекта (добавить поле в сущность + миграция;
  новый эндпоинт с тестом; починить падающий тест; отрефакторить сервис).
- Прогоняйте каждую конфигурацию (уровень 0 → 0+1 → 0+1+2 → +3) и фиксируйте:
  выходные токены, wall-clock, число итераций до зелёного, число ручных правок после.
- Отключайте по одному MCP-серверу и смотрите на дельту. Инструмент, который не окупает
  своё описание в контексте, надо выключать — Claude Code позволяет это через
  `disabledMcpServers` и `alwaysLoad: false`.
- Порог принятия решения простой: если конфигурация не даёт устойчивого выигрыша хотя бы
  по одной метрике на 5 задачах — она добавляет дисперсию, а не пользу.
