# CLAUDE.md — шаблон для Spring Boot проекта

> Скопируйте в корень проекта и вычистите всё, что к вам не относится.
> Правило простое: сюда попадает только то, что Клод нарушает без напоминания.
> Всё, что можно проверить машиной, должно жить в hook'ах или ArchUnit, а не здесь.

## Проект

- Стек: Java 21, Spring Boot 3.5.x, Gradle (Kotlin DSL), PostgreSQL, Flyway, Testcontainers.
- Модули: `app` (запуск), `domain` (сущности + бизнес-логика), `web` (REST), `infra` (адаптеры).
- Правило зависимостей: `web → domain`, `infra → domain`. `domain` не зависит ни от чего.

## Команды

```bash
./gradlew --offline compileJava compileTestJava   # быстрая проверка, <30 c
./gradlew --offline spotlessApply                 # формат
./gradlew --offline test --tests '*FooServiceTest' # точечный тест
./gradlew --offline test                          # полный прогон — только перед коммитом
./gradlew --offline test --tests 'ArchitectureTest' # архитектурные правила
```

Никогда не запускай `./gradlew build` для проверки правки — это минуты. Компиляция + затронутые тесты.

## Разделение инструментов (важно)

У тебя есть несколько путей к одной цели. Выбирай так:

| Нужно | Используй | Не используй |
|---|---|---|
| Поиск по тексту/паттерну | `Grep`, `Glob` | IDE MCP-поиск |
| Объявление символа, все usages, иерархия типов | IDE MCP | `Grep` — даст ложные срабатывания |
| Переименование символа | IDE MCP `rename_refactoring` | серию правок `Edit` |
| Ошибки и предупреждения | `mcp__ide__getDiagnostics` + `compileJava` | только глазами |
| Формат | `./gradlew spotlessApply` | ручное выравнивание |

**Деградация обязательна.** Инструменты IDE работают только при запущенной и проиндексированной
IDE. Если MCP-инструмент недоступен или вернул пустой результат — не считай это ответом
«ничего не найдено» и не выдумывай структуру проекта. Скажи об этом и переключись на
`Grep`/`Glob` и Gradle.

## Правила кода

### Внедрение зависимостей
- Только constructor injection, поля `private final`.
- `@Autowired` на поле запрещён (проверяется в `ArchitectureTest`).

### Транзакции
- `@Transactional` — на сервисном слое. Не на контроллере, не на репозитории.
- Читающие методы — `@Transactional(readOnly = true)`.
- Внутри транзакции нет сетевых вызовов к внешним сервисам.

### Persistence
- `spring.jpa.hibernate.ddl-auto` — только `validate`. Менять запрещено.
- **Любое изменение `@Entity` без миграции Flyway в том же изменении — незавершённая работа.**
  Миграции: `src/main/resources/db/migration/V{n}__{snake_case}.sql`. Существующие
  миграции не редактируются никогда — только новые.
- Связи `LAZY` по умолчанию. Для коллекций в ответе — `@EntityGraph` или `join fetch`.
- При добавлении выборки со связями — проверь N+1: включи
  `spring.jpa.properties.hibernate.generate_statistics=true` в тестовом профиле.

### Web
- Наружу отдаём DTO (`record`), никогда не сущности.
- Ошибки — через `@RestControllerAdvice` + `ProblemDetail` (RFC 7807).
- Валидация — `@Valid` + jakarta.validation на DTO, не ручные `if`.
- Новый эндпоинт → тест среза (`@WebMvcTest`) в том же изменении.

### Конфигурация
- `@ConfigurationProperties` + `@Validated`. Россыпь `@Value` — нет.
- Версии зависимостей — только через Spring Boot BOM. Ручные версии не добавлять.

### Логи
- SLF4J, параметризованные сообщения: `log.info("user {} created", id)`.
- `System.out.println` запрещён. Секреты и PII в логи не пишем.

### Тесты
- Срезы (`@DataJpaTest`, `@WebMvcTest`, `@JsonTest`) вместо `@SpringBootTest` везде,
  где это возможно: `@SpringBootTest` поднимает новый контекст и убивает время прогона.
- `@DirtiesContext` — только с обоснованием в комментарии.
- Testcontainers — через общий базовый класс с `@ServiceConnection`, не по одному на тест.
- Assertions — AssertJ.

## Архитектурные правила

Закодированы в `ArchitectureTest` (ArchUnit). После структурных изменений запускай:

```bash
./gradlew --offline test --tests 'ArchitectureTest'
```

Если правило мешает — обсуди изменение правила, не обходи его.

## Порядок работы над задачей

1. Понять контекст: модель домена, существующие паттерны в проекте. Сначала посмотри,
   **как уже сделано рядом**, потом предлагай своё.
2. План: что меняем, какие файлы, нужна ли миграция, какие тесты.
3. Правка.
4. `compileJava compileTestJava` + `mcp__ide__getDiagnostics` по изменённым файлам.
5. Затронутые тесты.
6. `spotlessApply`.
7. Отчёт: что сделано, что не сделано и почему.

Не сообщай об успехе, пока пункты 4–6 не прошли. Если тест падает — так и скажи, с выводом.
