# Выбор источника контекста

Цель — не «использовать IDE», а **не соврать**, когда IDE недоступна.

## Шаг 0. Предскажи, не вызывая инструментов

Выпиши гипотезу: какие пакеты, сущности, сервисы и контроллеры, скорее всего, участвуют
в задаче. Дальше ты проверяешь гипотезу, а не исследуешь проект с нуля. Это вдвое
сокращает число вызовов.

## Шаг 1. Проверь доступность семантического слоя

Проверяй именно так, до того как строить план:

1. Есть ли в списке инструментов `mcp__ide__getDiagnostics`?
2. Есть ли инструменты IDE MCP (поиск символов, `get_file_problems`)?
3. Есть ли Spring MCP (`get_project_summary`)?

Три возможных режима:

| Режим | Условие | Что делать |
|---|---|---|
| **Полный** | доступны IDE MCP + Spring MCP | символы и структуру брать из MCP, текстовый поиск — `Grep` |
| **Частичный** | только `mcp__ide__getDiagnostics` | структуру собирать `Glob`+`Grep`+`Read`, диагностику — из IDE |
| **Автономный** | ничего из перечисленного (CI, headless, IDE закрыта) | всё через `Glob`/`Grep`/`Read` и `./gradlew` |

**Назови выбранный режим вслух в ответе.** Пользователь должен знать, на чём основан вывод.

## Шаг 2. Правило пустого ответа

Пустой результат MCP-инструмента **не является** ответом «в проекте этого нет».
IDE могла быть в процессе индексации (dumb mode) или не запущена.

Если инструмент вернул пусто или явно неполно:

1. Не строй на этом выводов.
2. Перепроверь тем же вопросом через `Grep`/`Glob`.
3. Если расхождение есть — сообщи о нём и доверяй `Grep`.

## Шаг 3. Явный include/skip

Перечисли пути исследования и по каждому скажи «беру / пропускаю» с одной строкой
обоснования:

- структура модулей и зависимости
- доменные сущности
- репозитории
- сервисы
- DTO и мапперы
- REST-эндпоинты
- конфигурация и профили
- существующие тесты рядом

Пропуск с обоснованием дешевле, чем молчаливый пропуск: он видим и его можно оспорить.

## Шаг 4. Сырой вывод — в субагента

Если план содержит больше 3–4 вызовов с объёмным выводом — делегируй исполнение
субагенту `spring-explorer` и попроси вернуть синтез, а не сырые данные. Тонны JSON
не должны попадать в основной контекст.

## Шаг 5. Назови неозвученные ожидания

Прежде чем писать код, выпиши, что пользователь, скорее всего, подразумевал, но не сказал:
правила валидации, коды и формат ошибок, требования к авторизации, пагинация,
идемпотентность, транзакционные границы. Спроси только о том, что меняет реализацию;
остальное зафиксируй как принятое допущение.
